\chapter{Continual Learning and Membership Inference}
\label{ch:cl_mia}

The previous chapters established that the whuGAIT authentication pipeline is vulnerable to membership inference: both the delta-score attack and LiRA can distinguish member subjects from non-members with AUC well above chance. This chapter asks whether the CDML mechanism introduced for continual learning can be repurposed to reduce that exposure.

The intuition is the following. CDML applies a binary code $\mathbf{s}_k \in \{-1,+1\}^d$ to the Conv4 feature maps before the LSTM sees them. During CL training, different codes per task isolate gradients and prevent catastrophic forgetting. The same mechanism can be applied during the authentication phase with a single fixed key: the LSTM is trained on feature maps modulated by that key and subsequently only responds correctly when the same key is present at inference time. An attacker who queries the system without the key receives scrambled temporal structure that the LSTM was never trained to interpret, making it harder to extract a reliable membership signal.

The intended deployment model is the following. A developer trains the CNN backbone through CL and publishes the weights. Any operator who wants to deploy an authenticator trains a fresh LSTM on top of that backbone, modulated by their own private key. The key is never serialised into the checkpoint and is never shared; only the operator's inference server needs to hold it. This model allows the CNN to be distributed freely while the privacy surface of each deployment remains under the operator's control.

This chapter reports the design process rather than a single result. Each configuration was motivated by what the previous one showed, and the final solution emerged from the failure modes along the way.

\section{Threat Model and Key Design}
\label{sec:cl_threat}

The defence is designed around a specific threat model, and two simpler key designs fail for reasons that are worth stating explicitly before describing the implementation.

\textbf{Per-user keys are incompatible with CDML.} A natural first idea is to assign each enrolled user their own key, so that an attacker who obtains the system for one user cannot draw inferences about others. The CDML mechanism applies one binary code per task, where a task groups an entire operator's subject cohort for a single training round. Assigning each of the enrolled subjects a distinct code during LSTM training would require the LSTM to simultaneously learn as many separate authentication surfaces as there are subjects, which is not feasible. The key granularity is therefore constrained to be operator-level, not subject-level.

\textbf{The CNN cannot hold the key.} The CNN backbone is distributed to every operator: any party can download the same checkpoint and inspect it freely. If the privacy key were embedded in the CNN weights or applied at the CNN stage, every operator would possess it, and holding the key would confer no advantage to any particular deployment. The key must reside in a component that is not distributed. In the two-component pipeline, the only such component is the LSTM and the inference server that executes it. Inserting the code between the CNN output and the LSTM input is therefore the minimal architectural position that keeps the key outside the publicly available component.

These two constraints together define the threat model assumed throughout this chapter. The attacker is assumed to have full access to the CNN weights (they are public), no access to the LSTM weights (held server-side and never distributed), and no access to the key (never serialised into any checkpoint and never shared). Under this model, the attacker can query the CNN freely but cannot reconstruct the operator's authentication surface without the key. A wrong-key query produces feature maps whose signs are permuted in a pattern the LSTM was not trained to interpret, and the membership signal collapses. The correct key is the operational bottleneck: it is the only element that cannot be derived from publicly available artefacts.

\section{Experimental Setup}
\label{sec:cl_setup}

The 98 member subjects from Chapter~\ref{ch:system} are divided into four sequential CL tasks of 24 subjects each (96 members total). The 2 remaining subjects join the 20 held-out subjects to form a 22-subject non-member pool. The CDML encoder is trained with Adam ($\text{lr} = 10^{-3}$, batch 512, 100 epochs per task, $\gamma = 0.9$ schedule), one binary code $\mathbf{s}_k$ per task (seed $1000 + k$) applied at the Conv4 feature-map output before the flatten layer. After CL training the encoder is frozen and an LSTM authenticator is trained on top. The delta-MIA attack from Chapter~\ref{ch:mia} is applied unchanged.

\section{128-Dim Broadcast Key: First Approach}
\label{sec:cl_fm}

The simplest instantiation applies a single 128-element binary pattern uniformly across all 16 feature-map channels: $\tilde{F}_{b,c,i}(x) = F_{b,c,i}(x) \cdot s_i$, where $b$ indexes the batch, $c$ the channel, and $i$ the feature dimension. This preserves the inter-channel relationships the LSTM relies on for pairwise comparison and allows the authenticator to converge normally. The key is stored separately from the model weights and is never serialised into the \texttt{.pt} checkpoint. Figure~\ref{fig:fm_arch} illustrates both phases of the unified mechanism.

\subsection{Key Specificity and Operator Model}
\label{ssec:fm_operator}

The LSTM is completely key-specific: replacing the training key with any other seed reduces authentication accuracy to approximately 50\% (random). Key-invariance and privacy protection are in direct tension: training on randomly varying keys would remove the privacy guarantee because the LSTM would then respond to any key, including no key.

The key-specificity does not prevent deployment. An operator who obtains the CNN weights trains a fresh LSTM on features modulated by their own private key. The training key used by the original developer (seed~3000) is never shared. Figure~\ref{fig:fm_training_curves} shows that a fresh LSTM reaches competitive authentication accuracy within \fmOpConvergeEpoch{} epochs under any key.

\subsection{Two Problems with the 128-Dim Baseline}
\label{ssec:fm_limits}

The 128-dim results confirm that key conditioning works: a wrong key collapses the MIA signal to near chance. Two problems remain, however, and they motivate the design iterations in the following sections.

\paragraph{Accuracy drop on earlier tasks.}
Applying a broadcast code during CL training provides only moderate gradient isolation between tasks. Table~\ref{tab:cl_retention} (presented in Section~\ref{ssec:fm_keydim}) shows that tasks T1 and T2 retain noticeably lower accuracy under the 128-dim code compared to a stronger isolation configuration. This means that the privacy benefit comes partly at the cost of the system's primary function.

\paragraph{All-ones bypass.}
The defence assumes a model-as-a-service deployment where the key is enforced server-side. An attacker who obtains the full model weights can bypass the key by supplying the all-ones vector $\mathbf{1} \in \{-1,+1\}^d$, which is a valid element of the key space and leaves the feature maps completely unmodulated. The resulting no-key MIA AUC is \fmMIANoKey{}, matching the undefended baseline. Excluding degenerate keys from the valid key space, or retraining the LSTM with randomly varying keys, would close this bypass; both are left as future work for the 128-dim configuration.

\section{2048-Dim Per-Channel Key: A Failed Attempt}
\label{sec:cl_2048}

The accuracy problem with the 128-dim baseline suggests that stronger gradient isolation might help. An independent sign pattern per channel (a 2048-element code reshaped to $(16, 128)$) applies a different modulation to each of the 16 feature-map channels: $\tilde{F}_{b,c,i}(x) = F_{b,c,i}(x) \cdot s_{c,i}$, where $s_{c,i}$ is the sign assigned to channel $c$ at feature position $i$. This eliminates any shared structure across channels during CL training, which should in principle provide better gradient isolation.

In practice, the LSTM authenticator fails to converge under this configuration. Training stalls at around 50\% accuracy even with extended epochs. The reason is structural: the LSTM compares two windows by processing the concatenated feature maps of both over time. When every channel carries an independent sign pattern, there is no coherent relationship between channels for the LSTM to exploit. The per-channel scrambling that helps the CNN also destroys the temporal similarity signal the LSTM needs to learn pairwise authentication.

\section{2048-CNN / 128-LSTM Hybrid}
\label{ssec:fm_keydim}

The failure of the pure 2048-dim configuration suggests a decoupling: train the CNN with per-channel codes for strong gradient isolation, then train the LSTM authenticator on the frozen CNN backbone with a 128-dim broadcast key that restores inter-channel coherence. The CNN and LSTM now operate under different code dimensionalities at their respective training phases. The checkpoint written after CL training carries the 2048-dim weights; the LSTM is trained on features modulated by a separate 128-dim key and the CNN is never modified after the CL phase.

The hybrid addresses the accuracy problem: authentication accuracy rises from \fmOpAuthMean{} to \fmHybOpAuthMean{}, consistent with the stronger gradient isolation of the 2048-dim CNN producing more discriminative feature maps even when queried with a broadcast key.

\paragraph{Effect on the all-ones bypass.}
Under the 128-dim baseline, an attacker who applies the identity modulation recovers the full MIA signal (\fmMIANoKey{}). Under the hybrid, the same bypass yields a no-key AUC of \fmHybMIANoKey{}, near chance. The 2048-dim per-channel scrambling during CNN training is aggressive enough that the raw (unmodulated) feature maps carry no exploitable membership structure, even though the LSTM was trained on 128-dim modulated representations. Both problems identified in Section~\ref{ssec:fm_limits} are therefore addressed by the hybrid configuration.

\paragraph{Multi-seed robustness.}
A twelve-seed operator sweep (seeds 2000--14000) confirms that the result generalises across independently trained LSTMs. Mean authentication accuracy is \fmHybOpAuthMean{} ($\pm$\fmHybOpAuthStd{} pp), mean AUC under the operator's correct key is \fmHybOpAUCCorrectMean{} ($\pm$\fmHybOpAUCCorrectStd{}), and the no-key AUC is \fmHybOpAUCNoKeyMean{} ($\pm$\fmHybOpAUCNoKeyStd{}), consistent with chance across all seeds. The cosine similarity between each operator key and the developer key spans $[-0.19,\,+0.17]$, ruling out the possibility that the near-chance no-key result is an artefact of near-identical keys.

\paragraph{Remaining limitations.}
Two practical limitations apply. The best checkpoint is identified post-hoc by validation accuracy, which makes the reported figure optimistic relative to a deployment where the stopping point must be chosen before observing test performance. Additionally, the train--test accuracy gap of approximately 7 percentage points (train 92.4\%, test \fmHybOpAuthMean{}) suggests that the LSTM partially memorises the training pairs rather than learning a fully generalisable similarity function; the gap would likely narrow with a larger training pool or stronger regularisation, but this is left to future work.
